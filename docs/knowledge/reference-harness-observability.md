# Knowledge: reference harness comparison

Status: official-source maintenance comparison, checked 2026-09-07

## Conclusion

**Inference:** 6〜12か月のproduct寿命を考えても、参照Harnessの工程図へ全面改築する根拠はない。既存のcontext境界を起点に、正本データ、表示、schema互換、復旧の責任を段階的に整理する方が妥当である。小さな見た目の整理だけで十分という意味ではない。callerが保存形式や旧世代の状態を知る必要がある境界は、独立した受入条件で構造を見直す対象になる。

比較で直接役立つのはCodex Securityのcanonical contractとprojectionの分離、Anthropicの明示的な失敗分類、両者の境界を検証するtestである。stage数、Module数、総LOCは保守性の証明にならない。AVDHとCloudflareの記事は評価観点の根拠にはなるが、非公開のInterfaceや復旧保証の実装根拠にはならない。

**Exploration comparison / Inference:** 探索手法の本質的な差はagent数ではなく、何をfrontierとして保持し、次のworkを誰が決め、何をcoverageと呼ぶかにある。static analysisは人がqueryへ符号化した仮説、coverage-guided fuzzingは到達したruntime edgeとinput corpus、manual researchは研究者の更新するsemantic hypothesisをfrontierにする。公開されたagentic Harnessはmanual researchの一部を外部stateと複数roleへ移すが、その構成も一様ではない。

Local Harnessの直接の設計系譜は一般的なagentic Harnessではなく、wp2shellがsecurity research向けに翻案したOpenAI Cycle Double Cover Promptである。外部Harnessは、そこから責務を分離した現設計を相対化する比較対象として扱う。

このnoteは外部根拠と推論を記録する。設計採用、現行実装の一覧、次の作業の正本はそれぞれ[Architecture](../ARCHITECTURE.md)、[Codebase Guide](../CODEBASE-GUIDE.md)、GitHub Issuesとする。

## Exploration methods: what becomes the frontier

### Primary design lineage: wp2shell / Cycle Double Cover Prompt

| --- | --- | --- | --- |

| Frontier state | Prompt内のroot agentがapproach registry、blocked route、remaining gapを管理し、新mechanismがある場合だけblocked routeを再開する。 | Hypothesis、Route Fragment、Frontier Gap、Approach Family、Depth Work ItemをCAS / Ledgerへtyped artifactとして保存する。 | wp2shellでconversation内にあったfrontierをHarness-owned stateへ移した部分は実装上の主要な深化である。 |
| Iteration | root agentが各Waveをsynthesize、challenge、redirectし、新しいroundを繰り返す。最初のWaveや各agentのno-findingで止めない。 | current v7は初期Wave後にRoot Evaluationを行い、DepthではRoot Synthesis、source-aware Critic、fresh Depth Evaluationを一round実行する。current pathは追加のMissing-link Finder Waveとfresh Closure reviewをmaterializeしない。 | **Conditional Depth gap:** wp2shell / CDCの反復的な新証拠取得は設計・legacy codeにはあるが、current executable loopにはない。これは初期Waveで見つかった単独の重大Findingを成立させる前提ではなく、複雑なgapや追加escalationをAIが追う場合の不足である。 |

**Inference:** Local Harnessはwp2shell Promptへ別のPromptを足したものではない。wp2shell / CDCでroot agentと長大Promptが所有していたportfolio、registry、budget、record、audit、iterationを、Campaign Control、typed artifact、fresh roleへ分解する試みである。通常Waveの中心評価は、独立familyからunauthenticated Stored XSS、SQLi等のhigh-impact semanticsを発見し、AIがfresh Validationへ送れるかである。具体的gapから新しいFinder roundを起動してchainを伸ばす能力はconditional Depthの評価軸であり、全Findingへ要求しない。

### Conventional methods

| Method | Search-space construction and candidate generation | Depth, tools, and oracle | Stopping, coverage, and decision owner |
| --- | --- | --- | --- |
| Static / dataflow analysis | **Observed / docs:** CodeQLのpath queryはquery authorがsource、sink、両者を結ぶflowを定義し、そのmodel内のpathを結果にする。[Path query](https://codeql.github.com/docs/writing-codeql-queries/creating-path-queries/)と[data-flow analysis](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-javascript-and-typescript/)はlocal flowを高速・高精度だが不完全、global flowをより強力だが高costで低精度になり得るものとして区別する。 | query suite、framework model、barrier、additional flow stepを人が調整し再実行する。flowが途切れる箇所は[partial flow](https://codeql.github.com/docs/writing-codeql-queries/debugging-data-flow-queries-using-partial-flow/)で調べる。結果は潜在問題のalertであり、GitHubのworkflowも人がdismiss / fix / reopenする。[Alert management](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts) | 選択suiteの完走は、抽出できたcodeと選択query / model内での列挙完了であり、未知のsecurity semanticsの完了証明ではない。**Inference:** engineは事前定義された仮説の展開を所有し、security-relevantなsource / sink / flowを定義する研究判断はquery / model authorが所有する。 |
| Coverage-guided fuzzing / dynamic analysis | **Observed / docs:** AFL++はinstrumented target、harness、seed corpusから始め、mutationが新しいedge / state transitionを作るとcorpusへ保持し、そこから更にmutationする。[Approach](https://aflplus.plus/docs/afl-fuzz_approach/)と[in-depth guide](https://aflplus.plus/docs/fuzzing_in_depth/)。frontierはconcrete inputと到達coverageであり、semantic hypothesisではない。 | depthはseedから子孫inputへのmutation ancestry。標準oracleはcrash、hang、sanitizer等であり、non-crashのlogic bugには人がround-trip、differential result、不変条件などをexecutable oracleへ変換する。[AFL++ beyond crashes](https://aflplus.plus/docs/fuzzing_in_depth/#j-going-beyond-crashes)と[libFuzzer](https://llvm.org/docs/LibFuzzer.html) | defaultは継続実行で、時間 / execution上限やcoverage停滞を人が判断する。AFL++もfull coverageは通常不可能で、停滞時にseedやmutatorの変更余地があるとする。[Coverage check](https://aflplus.plus/docs/fuzzing_in_depth/#g-checking-the-coverage-of-the-fuzzing)。**Inference:** fuzzerは局所input探索を所有するが、harness、oracle、重要surface、budgetは人が所有する。 |
| Manual semantic / business-logic research | **Observed / docs:** OWASP WSTGはrequirements、use case、documentationからworkflowを理解し、stepのskip / repeat / reorder、parameter tampering、想定外順序などのmisuse caseを作る。[Business logic introduction](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/00-Introduction_to_Business_Logic/)と[workflow circumvention](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/06-Testing_for_the_Circumvention_of_Work_Flows) | proxy等は観測と操作を助けるが、観測結果から次のhypothesis、handoff、hidden invariantを選ぶのは研究者。[Business-logic data validation](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/01-Test_Business_Logic_Data_Validation)はintended ruleと実挙動を比較する。 | WSTGはbusiness logic testingをtesterのskill、creativity、business-process knowledgeに依存するmanual workと位置づける。**Inference:** use caseを列挙できてもsemantic closureの機械的証明はなく、深掘りと停止の判断も研究者が所有する。 |

この節は外部Referenceの事実ではなく、現在のrepository source、Behavior Test、公開済み実測から比較する。実装状態の正本は[Codebase Guide](../CODEBASE-GUIDE.md#research)、研究方針の正本は[Research Design](../RESEARCH-DESIGN.md)である。

## Reusable maintenance judgement for 6–12 months

以下は採用済み設計ではなく、上の比較に基づく判断材料である。

1. **全面rewriteを選ぶ理由は不足している。** Codex Securityはconsumer向けcanonical contract、Anthropicは狭い用途のreference、AVDH / Cloudflareは内部運用であり、どれも現行productの代替実装ではない。特に保守終了のreferenceを取り込むと、互換性と修正の責任も引き受けることになる。
2. **段階的な構造整理には根拠がある。** 正本recordとprojection、current writeとlegacy read、実行終了とdomain outcomeの責任がcallerへ漏れている場合は、その境界一つを受入条件にして整理する。旧artifactを再読込みできることとcurrent pathのInterfaceが単純になることを同時に確認する。
3. **最小化の単位はModule数ではなくcaller knowledgeにする。** 外側APIが短くても、内部callerが保存順、旧schema、provider streamを知れば変更が広がる。逆に一つのownerがこれらを隠し、public seamから成功・失敗・再読込みを検証できるなら、内部のcode量だけで浅いModuleと断定しない。
4. **保証はtestと観測に結びつける。** crash recovery、schema互換、late result、隔離、承認bindingは異なる性質である。公式文書の表現やdefault suiteの成功だけで一括して保証せず、どの境界をどの条件で確認したかを残す。

調査では固定commitのsource / tests / docsと公式記事だけを読んだ。参照Harnessのinstall、build、test、scan、target runtime、model呼出しは実行していない。
